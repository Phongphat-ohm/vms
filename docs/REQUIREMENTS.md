# เอกสารข้อกำหนดระบบ (System Requirements Specification)
## Smart Village Management System (VMS) — ระบบบริหารหมู่บ้านอัจฉริยะ

---

## 1. บทนำและวัตถุประสงค์ (Introduction & Purpose)

ระบบ **Smart Village Management System (VMS)** ได้รับการออกแบบขึ้นเพื่อเป็น **แพลตฟอร์มศูนย์กลางการบริหารจัดการหมู่บ้านอัจฉริยะ (Unified Smart Village Management Hub)** ที่รวบรวมหลากหลายระบบงานและบริการชุมชนเข้าไว้ด้วยกันในที่เดียว โดยมีระบบงานแกนหลัก (Foundational Core Systems) ได้แก่:
1. ระบบทะเบียนประชากรดิจิทัล (Digital Population Registry)
2. ระบบบ้านและผังครัวเรือน (Households & Residence Mapping)
3. ระบบคลังเอกสารและหลักฐานราชการชุมชน (Community Document Storage)
4. ระบบบริหารจัดการสิทธิ์ผู้ใช้งานและการรักษาความปลอดภัย (Granular RBAC & Security)
5. ระบบบันทึกประวัติการตรวจสอบการทำงานแบบห้ามแก้ไข (Append-only Audit Trail)

ระบบถูกออกแบบภายใต้หลักการ **Security by Design**, **Privacy by Design**, และสอดคล้องกับ **พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA)** พร้อมโครงสร้างสถาปัตยกรรมแบบเปิดที่รองรับการบริหารจัดการแบบหลายหมู่บ้าน (Multi-Village Architecture) และพร้อมบูรณาการระบบบริการชุมชนอื่น ๆ ของหมู่บ้านมารวมไว้ในแพลตฟอร์มเดียวได้อย่างไร้รอยต่อ (เช่น ระบบกองทุนหมู่บ้าน, สัจจะออมทรัพย์, ระบบน้ำประปาชุมชน, และระบบแจ้งข่าวสารฉุกเฉิน)

---

## 2. กลุ่มผู้ใช้งานระบบ (User Personas)

1. **SYSTEM_ADMIN (ผู้ดูแลระบบสูงสุด)**: ดูแลโครงสร้างระบบส่วนกลาง จัดการบัญชีหมู่บ้าน ตั้งค่าความปลอดภัยระดับเซิร์ฟเวอร์ และตรวจสอบภาพรวมทั้งระบบ
2. **VILLAGE_ADMIN (ผู้ดูแลระบบระดับหมู่บ้าน / ผู้ใหญ่บ้าน / ประธานชุมชน)**: จัดการผู้ใช้งานและสิทธิ์ของเจ้าหน้าที่ภายในหมู่บ้าน กำหนดค่าเฉพาะของหมู่บ้าน ดูประวัติ Audit Log และรายงานภาพรวม
3. **STAFF (เจ้าหน้าที่บันทึกและจัดการข้อมูล / ผู้ช่วยผู้ใหญ่บ้าน / อสม.)**: บันทึก แก้ไข ค้นหาข้อมูลประชากร บ้าน ครัวเรือน และจัดการเอกสารแนบตามขอบเขตงานที่ได้รับมอบหมาย
4. **VIEWER (ผู้ตรวจดูข้อมูล / คณะกรรมการตรวจสอบ)**: ค้นหาและดูข้อมูลเฉพาะส่วนที่ได้รับอนุญาตแบบ Read-Only ไม่สามารถแก้ไขข้อมูลและไม่สามารถดูข้อมูลอ่อนไหวโดยตรงได้

## 3. ขอบเขตและข้อกำหนดเชิงฟังก์ชัน (Functional Requirements)

### 3.1 Module 1: การยืนยันตัวตนและความปลอดภัยของเซสชัน (Authentication & Session)
- **FR-AUTH-01**: เข้าสู่ระบบด้วย Email และ Password ผ่าน Supabase Auth Engine (Self-hosted)
- **FR-AUTH-02**: ออกจากระบบ (Logout) และล้าง Session Token ใน Server-side HttpOnly Cookie ทันที
- **FR-AUTH-03**: ระบบลืมรหัสผ่าน (Forgot Password) และส่งลิงก์ตั้งรหัสผ่านใหม่ (Reset Password) ไปยังอีเมลที่ยืนยันแล้ว
- **FR-AUTH-04**: การเปลี่ยนรหัสผ่าน (Change Password) โดยต้องยืนยันรหัสผ่านเดิมก่อนทุกครั้ง
- **FR-AUTH-05**: การหมดอายุของเซสชัน (Session Timeout) เมื่อไม่มีกิจกรรมต่อเนื่องตามระยะเวลาที่กำหนด (Inactivity Timeout)
- **FR-AUTH-06**: การเปิด/ปิดการใช้งานบัญชี (Account Activation/Deactivation) โดยผู้ดูแลระบบ
- **FR-AUTH-07**: รองรับ Multi-Factor Authentication (MFA / TOTP) สำหรับผู้ดูแลระบบ
- **FR-AUTH-08**: บันทึกเหตุการณ์ความปลอดภัย (Login Security Events) ได้แก่ ความพยายาม Login สำเร็จ/ล้มเหลว, IP Address, User-Agent
- **FR-AUTH-09**: ป้องกัน Brute Force Attack ด้วยการจำกัดอัตราคำขอ (Rate Limiting) และชะลอ/ล็อกบัญชีชั่วคราวเมื่อกรอกผิดซ้ำ

### 3.2 Module 2: การจัดการข้อมูลประชากร (Population Management)
- **FR-POP-01**: บันทึกข้อมูลประชากรรายบุคคล ประกอบด้วย:
  - รหัสบุคคลภายใน (Internal UUID)
  - รหัสรันประชากร (Person Code เช่น `P-YYYY-XXXXX`)
  - เลขประจำตัวประชาชน 13 หลัก (เข้ารหัส AES-256-GCM + ทำ Blind Index)
  - คำนำหน้าชื่อ (นาย, นาง, นางสาว, ด.ช., ด.ญ., อื่นๆ)
  - ชื่อ และ นามสกุล
  - วันเดือนปีเกิด (และคำนวณอายุอัตโนมัติ)
  - เพศสภาพตามทะเบียน (ชาย, หญิง)
  - สัญชาติ และ ศาสนา
  - เบอร์โทรศัพท์ และ ช่องทางติดต่อ
  - อาชีพ และ ระดับการศึกษาสูงสุด
  - สถานะการมีชีวิต (มีชีวิต, ถึงแก่กรรม พร้อมวันที่)
  - วันที่เพิ่มข้อมูล, ผู้สร้างข้อมูล, ผู้แก้ไขล่าสุด
- **FR-POP-02**: ค้นหาข้อมูลประชากรด้วย ชื่อ, สกุล, รหัสบุคคล หรือเลขบัตรประชาชน (ค้นหาผ่าน Blind Index แบบ Exact Match)
- **FR-POP-03**: การกรองข้อมูล (Filter) ตาม เพศ, ช่วงอายุ, สถานะการมีชีวิต, กลุ่มอาชีพ, หมู่บ้าน
- **FR-POP-04**: การแบ่งหน้า (Pagination) และการเรียงลำดับ (Sorting) ตามชื่อ วันที่เพิ่มข้อมูล หรืออายุ
- **FR-POP-05**: การตรวจสอบข้อมูลซ้ำ (Duplicate Detection) โดยป้องกันการบันทึกเลขบัตรประชาชนซ้ำในระบบ
- **FR-POP-06**: ดูประวัติการแก้ไขข้อมูลรายบุคคล (Field-level Change History)
- **FR-POP-07**: แนบเอกสารส่วนบุคคล (เช่น สำเนาบัตรประชาชน, สูติบัตร) พร้อมเข้ารหัสการเข้าถึง
- **FR-POP-08**: การเก็บถาวร (Archive / Soft Delete) และการกู้คืน (Restore) ภายใต้สิทธิ์ผู้ดูแลระบบ
- **FR-POP-09**: การส่งออกข้อมูล (Export to Excel/CSV) จำกัดเฉพาะผู้มีสิทธิ์ `person.export` โดยมีการ Mask ข้อมูลอ่อนไหวและบันทึก Audit Log

### 3.3 Module 3: การจัดการบ้าน ครัวเรือน และทะเบียนบ้าน (Household & House Management)
- **FR-HOUSE-01**: การแยก Entity อย่างเด็ดขาด:
  - **บ้าน (House)**: ตัวอาคาร/สิ่งปลูกสร้างทางกายภาพ (เลขที่บ้าน, หมู่ที่, พิกัด GPS, ลักษณะสิ่งปลูกสร้าง)
  - **ครัวเรือน (Household)**: หน่วยทางสังคม/เศรษฐกิจที่อาศัยอยู่ร่วมกันในบ้านหลังนั้น (1 บ้านอาจมีมากกว่า 1 ครัวเรือนในกรณีเช่าแยกห้อง)
  - **บุคคล (Person)**: ตัวบุคคลรายเดี่ยว
  - **สมาชิกครัวเรือน (Household Membership)**: ความสัมพันธ์ระหว่างบุคคลกับครัวเรือน
  - **เอกสารทะเบียนบ้าน (House Registration Document)**: ข้อมูลและไฟล์สำเนาทะเบียนบ้าน (ท.ร.14)
- **FR-HOUSE-02**: จัดเก็บและแยกแยะประเภทการอยู่อาศัย (Residency Scope):
  - **ตามทะเบียนราษฎร์ทางการ (Official)**: เจ้าบ้านตามทะเบียนราษฎร์, ผู้อยู่อาศัยตามทะเบียนราษฎร์ (ตรงกับเล่ม ท.ร.14)
  - **ผู้อยู่อาศัยจริง / ประชากรแฝง (Actual Resident)**: ผู้เช่า, แรงงาน, ผู้มาพำนักประจำที่ไม่มีชื่อในเล่ม ท.ร.14
  - **มีชื่อแต่ไม่อยู่จริง (Official Absence)**: มีชื่อในเล่ม ท.ร.14 แต่ไปทำงาน/ศึกษาต่างถิ่น
- **FR-HOUSE-03**: จัดการสมาชิกครัวเรือน: กำหนดหัวหน้าครัวเรือน (Household Head), สมาชิก, ความสัมพันธ์กับหัวหน้าครัวเรือน
- **FR-HOUSE-04**: การย้ายที่อยู่:
  - ย้ายบุคคลเข้าบ้าน/ครัวเรือน (Move In)
  - ย้ายบุคคลออกจากบ้าน/ครัวเรือน (Move Out)
  - ย้ายบุคคลสลับระหว่างบ้านภายในหมู่บ้าน (Transfer Between Houses)
- **FR-HOUSE-05**: ทุกกระบวนการย้ายต้องทำงานภายใต้ **Database Transaction** และบันทึกประวัติเหตุการณ์ลงตาราง `household_events` โดย **ห้ามลบประวัติย้อนหลัง**
- **FR-HOUSE-06**: การแนบและตรวจสอบเอกสารเล่มทะเบียนบ้าน

### 3.4 Module 4: การจัดการผู้ใช้ สิทธิ์ และความปลอดภัย (User & Permission Management)
- **FR-USER-01**: ผู้ดูแลระบบจัดการผู้ใช้งาน (เพิ่ม, แก้ไข, ระงับบัญชี, ปลดล็อก)
- **FR-USER-02**: Dynamic Role-Based Access Control (RBAC):
  - สร้างบทบาทใหม่ (Custom Roles) หรือแก้ไขบทบาทเดิม
  - กำหนด Permission ให้แต่ละ Role อย่างละเอียด (Granular Registry)
  - มอบหมายบทบาทให้แก่ผู้ใช้ (User Role Assignment)
- **FR-USER-03**: กำหนดขอบเขตหมู่บ้านที่ผู้ใช้เข้าถึงได้ (Village User Access Scope)
- **FR-USER-04**: บันทึกประวัติการเปลี่ยนแปลงสิทธิ์ (Permission Assignment Audit)
- **FR-USER-05**: การตรวจสอบสิทธิ์อย่างเด็ดขาดที่ Server-side ในทุก Protected Operation

### 3.5 Module 5: การตั้งค่าหมู่บ้านและระบบ (Village & System Settings)
- **FR-SET-01**: การตั้งค่าข้อมูลหมู่บ้าน (ชื่อ, หมู่ที่, ตำบล, อำเภอ, จังหวัด, รหัสไปรษณีย์, ตราสัญลักษณ์, ช่องทางติดต่อ)
- **FR-SET-02**: การตั้งค่าส่วนบุคคลของผู้ใช้งาน (ชื่อแสดงผล, เปลี่ยนรหัสผ่าน, เปิดใช้งาน MFA)
- **FR-SET-03**: การตั้งค่าระบบส่วนกลาง (นโยบายขนาดไฟล์สูงสุด, รูปแบบไฟล์ที่อนุญาต, นโยบายการสำรองข้อมูล)
- **FR-SET-04**: ห้ามจัดเก็บ API Keys, Database Passwords หรือ Secret ในตาราง Settings ทั่วไป

### 3.6 Module 6: การจัดการเอกสารและไฟล์แนบ (Document & File Management)
- **FR-DOC-01**: จัดเก็บไฟล์ใน Supabase Storage Private Bucket โดยไม่มี Public Access
- **FR-DOC-02**: การตั้งชื่อไฟล์บน Storage ใช้ UUID v4 ห้ามใช้เลขบัตรประชาชนหรือชื่อบุคคลเป็น Path โดยตรง
- **FR-DOC-03**: ตรวจสอบ MIME Type และ Magic Bytes ของไฟล์อัปโหลดอย่างเข้มงวด (ป้องกันไฟล์อันตราย/Script)
- **FR-DOC-04**: จำกัดขนาดไฟล์อัปโหลด (เช่น เอกสารไม่เกิน 10MB, รูปภาพไม่เกิน 5MB)
- **FR-DOC-05**: การดาวน์โหลดไฟล์ผ่าน Short-lived Signed URL ที่มีอายุไม่เกิน 60 วินาที และต้องผ่านการตรวจสอบสิทธิ์
- **FR-DOC-06**: จัดการความสัมพันธ์ระหว่าง Database Record กับ Storage Object พร้อมกระบวนการลบแบบ Two-phase ป้องกัน Orphan Files

### 3.7 Module 7: การบันทึกประวัติการทำงาน (Audit & Activity Logs)
- **FR-LOG-01**: บันทึก Audit Log แบบ Append-Only ห้ามมี API แก้ไขหรือลบ Log
- **FR-LOG-02**: รายละเอียดที่บันทึก: ผู้ดำเนินการ, วันเวลา (ISO 8601 UTC), โมดูล, การกระทำ (Action), Entity ID, Village ID, IP Address, User-Agent, รายละเอียดความเปลี่ยนแปลง (Safe Delta JSON)
- **FR-LOG-03**: บันทึกเหตุการณ์เปิดดูข้อมูลอ่อนไหว (Sensitive Data Access) เช่น การกดดูเลขบัตรประชาชนตัวเต็ม
- **FR-LOG-04**: ทำการ Sanitization ห้ามมีรหัสผ่าน, Private Token, หรือเลขบัตรประชาชนตัวเต็มหลุดเข้าไปใน Log Payload

## 4. ข้อกำหนดที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)

### 4.1 ความมั่นคงปลอดภัยและการปฏิบัติตามกฎหมาย (Security & Compliance)
- **NFR-SEC-01**: ปฏิบัติตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) อย่างเคร่งครัด
- **NFR-SEC-02**: ข้อมูลเลขประจำตัวประชาชนต้องถูกเข้ารหัสด้วย AES-256-GCM (Ciphertext) และ HMAC-SHA256 (Blind Index)
- **NFR-SEC-03**: การสื่อสารทุกช่องทางต้องเข้ารหัสผ่าน HTTPS (TLS 1.3)
- **NFR-SEC-04**: ป้องกันภัยคุกคามตามมาตรฐาน OWASP Top 10 (Injection, XSS, CSRF, IDOR, SSRF, Broken Access Control)
- **NFR-SEC-05**: ยึดหลัก **Deny by Default** — หากไม่มีสิทธิ์ระบุไว้อย่างชัดเจน ให้ปฏิเสธการเข้าถึงทันที

### 4.2 ประสิทธิภาพและทรัพยากร (Performance & Resource Constraints)
- **NFR-PERF-01**: ระบบต้องทำงานได้อย่างราบรื่นบน Ubuntu VPS ที่มีทรัพยากรจำกัด (เริ่มต้นที่ 2 vCPU, RAM 4GB)
- **NFR-PERF-02**: เวลาตอบสนองของ API ทั่วไปเฉลี่ยไม่เกิน 300ms ภายใต้ Concurrent Users ไม่ต่ำกว่า 50 ผู้ใช้
- **NFR-PERF-03**: การค้นหาข้อมูลประชากรด้วยชื่อหรือเลขบัตรประชาชนต้องใช้เวลาประมวลผลฐานข้อมูลไม่เกิน 50ms ด้วย Indexing Strategy ที่เหมาะสม

### 4.3 ความถูกต้องและบูรณภาพของข้อมูล (Data Integrity & Reliability)
- **NFR-INT-01**: การย้ายบุคคล การเปลี่ยนแปลงสมาชิกครัวเรือน ต้องทำงานผ่าน ACID Transactions
- **NFR-INT-02**: ฐานข้อมูลต้องใช้ Foreign Key Constraints, Unique Constraints, และ Check Constraints เพื่อป้องกัน Orphan Data
- **NFR-INT-03**: มีระบบสำรองข้อมูลอัตโนมัติ (Automated Database Backup) ทุกวัน และเข้ารหัสไฟล์ Backup ก่อนจัดเก็บ

### 4.4 การบำรุงรักษาและการขยายระบบ (Maintainability & Extensibility)
- **NFR-MAINT-01**: สถาปัตยกรรม Modular Monolith แยกโดเมนชัดเจนในไดเรกทอรี `src/modules/`
- **NFR-MAINT-02**: ปราศจาก Circular Dependency ระหว่างโมดูล
- **NFR-MAINT-03**: รองรับการเพิ่มโมดูลใหม่ในอนาคต (เช่น กองทุนหมู่บ้าน, สวัสดิการ) โดยแก้ไขโค้ดส่วนกลางน้อยที่สุด

## 5. กฎทางธุรกิจสำคัญ (Critical Business Rules)

1. **BR-01 (ความไม่ซ้ำซ้อนของเลขบัตรประชาชน)**: บุคคลที่มีชีวิตอยู่ในระบบต้องไม่มีเลขประจำตัวประชาชนซ้ำกันภายในระบบ
2. **BR-02 (การแยกประเภทการอยู่อาศัย)**:
   - บุคคล 1 คนสามารถมีสถานะ **"ตามทะเบียนราษฎร์ (Official)"** ได้เพียง 1 บ้านในเวลาเดียวกัน
   - บุคคล 1 คนอาจมีสถานะ **"ผู้อยู่อาศัยจริง (Actual Resident)"** ในบ้านอื่นได้ แต่ต้องระบุความสัมพันธ์และสถานะชัดเจน
3. **BR-03 (หัวหน้าครัวเรือน)**: แต่ละครัวเรือนต้องมีหัวหน้าครัวเรือน (Household Head) ได้เพียง 1 คนในขณะใดขณะหนึ่ง หากย้ายหัวหน้าครัวเรือนออก ระบบต้องบังคับให้แต่งตั้งหัวหน้าครัวเรือนคนใหม่
4. **BR-04 (การบันทึกประวัติการย้าย)**: ห้ามลบข้อมูลการย้ายที่อยู่ออกจากระบบ ทุกการย้ายเข้า/ย้ายออกต้องเกิดเรคคอร์ดใน `household_events`
5. **BR-05 (การคุ้มครองข้อมูลอ่อนไหว)**: เจ้าหน้าที่ทั่วไปจะเห็นเลขบัตรประชาชนในรูปแบบ Mask (`1-XXXX-XXXXX-XX-X`) เท่านั้น ผู้ที่มีสิทธิ์ `person.sensitive.read` เท่านั้นจึงจะสามารถคลิกดูเลขเต็มได้ และทุกการคลิกดูจะถูกบันทึก Audit Log พร้อมระบุเหตุผล
6. **BR-06 (Multi-Village Data Isolation)**: เจ้าหน้าที่ของหมู่บ้านใดจะไม่มีสิทธิ์เข้าถึงหรือมองเห็นข้อมูลของหมู่บ้านอื่นเด็ดขาด เว้นแต่ผู้ใช้ระดับ `SYSTEM_ADMIN`

## 6. เกณฑ์การยอมรับของระบบ (System Acceptance Criteria)

- [ ] ผู้ดูแลระบบสามารถสร้างและกำหนดสิทธิ์ผู้ใช้ได้อย่างละเอียดตาม Permission Registry
- [ ] เจ้าหน้าที่สามารถค้นหาประชากรด้วยเลขบัตรประชาชนผ่าน Blind Index ได้อย่างถูกต้องโดยไม่มีการจัดเก็บ Plaintext
- [ ] สามารถย้ายสมาชิกในครัวเรือนได้ถูกต้อง ข้อมูลประวัติการย้ายถูกบันทึกครบถ้วน และไม่เกิดความผิดพลาดของข้อมูล (Zero Orphan Records)
- [ ] ไฟล์เอกสารที่อัปโหลดทั้งหมดถูกจัดเก็บใน Supabase Storage แบบ Private และดาวน์โหลดได้เฉพาะผ่าน Signed URL ที่มีอายุจำกัด
- [ ] ทุกการกระทำที่สำคัญ (Create/Update/Delete/View Sensitive/Export) ถูกบันทึกลง Audit Log และไม่สามารถแก้ไขหรือลบย้อนหลังได้
- [ ] ระบบผ่านการทดสอบ Automated Tests (Unit, Integration, E2E) และ Security Verification
